┌─────────────────────────────────────────────────────────────────────────────────┐
│                              记忆系统设计                                        │
│                                                                                 │
│  Q: 为什么用5层记忆架构，而不是一张大表？                                       │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: 5层分表                                                          │    │
│  │  替代方案: 一张大表                                                     │    │
│  │  理由:                                                                  │    │
│  │  • 查询效率: 按类型查询更快 (facts查8种类型 vs 全表扫描)                │    │
│  │  • 生命周期管理: 不同层有不同的清理策略                                 │    │
│  │  • 数据隔离: 情绪数据和事实数据分开存储                                 │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么Fact用Upsert而不是Insert？                                           │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: Upsert (同subject+fact_type更新)                                 │    │
│  │  替代方案: 每次Insert新记录                                             │    │
│  │  理由:                                                                  │    │
│  │  • 去重: 避免"喜欢Python"重复10次                                       │    │
│  │  • 保持最新: 用户说"现在喜欢Go了" → 更新而非新增                        │    │
│  │  • 减少噪音: 152条 → 30-40条                                           │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么Fact分层过滤？                                                        │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: 稳定画像全保留，临时事件只保留7天                                │    │
│  │  替代方案: 全量注入                                                     │    │
│  │  理由:                                                                  │    │
│  │  • 减少prompt噪音: 152条 → 30-40条                                     │    │
│  │  • 聚焦重要信息: "喜欢Python"比"7月20日去了四川"更重要                 │    │
│  │  • 控制token消耗: prompt太长会增加成本和延迟                           │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么向量存储用SQLite BLOB而不是FAISS/ChromaDB？                           │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: SQLite BLOB (struct.pack序列化float32)                           │    │
│  │  替代方案: FAISS/ChromaDB                                               │    │
│  │  理由:                                                                  │    │
│  │  • 零依赖: 不需要额外安装向量数据库                                    │    │
│  │  • 部署简单: 所有数据在一个memory.db文件                               │    │
│  │  • 项目规模: 个人助手场景数据量不大，SQLite够用                        │    │
│  │  权衡: 大规模多用户场景应该用Qdrant/Milvus                             │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么Embedding缓存用SQLite而不是Redis？                                    │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: SQLite cache-aside                                               │    │
│  │  替代方案: Redis                                                        │    │
│  │  理由:                                                                  │    │
│  │  • 零依赖: 不需要额外部署Redis服务                                     │    │
│  │  • 单用户够用: 个人助手场景不需要分布式缓存                            │    │
│  │  • 持久化: SQLite天然持久化，Redis需要额外配置                         │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│                              LLM相关设计                                        │
│                                                                                 │
│  Q: 为什么用Ollama+OpenAI双后端？                                               │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: 工厂模式切换                                                     │    │
│  │  替代方案: 只用一个后端                                                 │    │
│  │  理由:                                                                  │    │
│  │  • Ollama: 本地部署，零成本，隐私保护，适合embedding                   │    │
│  │  • OpenAI: 云端API，质量更高，适合对话                                 │    │
│  │  • 工厂模式: create_llm_provider()根据配置自动创建                     │    │
│  │  • Embedding固定用Ollama: 云端API通常不支持embedding                   │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么信息抽取用Fire-and-forget？                                           │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: 异步提取，不阻塞回复                                             │    │
│  │  替代方案: 同步等待提取完成                                             │    │
│  │  理由:                                                                  │    │
│  │  • 用户体验: 先返回回复，再异步提取                                    │    │
│  │  • 响应速度: 提取可能需要1-2秒，不能让用户等                           │    │
│  │  • 降级策略: 提取失败不影响回复                                        │    │
│  │  权衡: 可能丢失一些记忆，但保证响应速度                                │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么学习识别从关键词改为LLM？                                             │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: LLM智能判断 (合并到抽取prompt)                                   │    │
│  │  替代方案: 关键词匹配                                                   │    │
│  │  理由:                                                                  │    │
│  │  • 覆盖面广: "我在做skill系统"不包含"学/看/读"动词                     │    │
│  │  • 0额外延迟: 合并到现有抽取流程，不增加LLM调用                        │    │
│  │  • 准确率高: LLM能理解语义，远高于关键词                               │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么任务检测用正则+LLM混合？                                              │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: 列表检测用正则，完成检测用LLM                                    │    │
│  │  替代方案: 纯LLM                                                        │    │
│  │  理由:                                                                  │    │
│  │  • "今日任务：A；B；C"格式固定，正则100%准确，0延迟，0成本            │    │
│  │  • "实验完成了"的语义理解需要LLM，正则只能覆盖固定表达                 │    │
│  │  • 混合方案比纯LLM更可靠，比纯规则更灵活                               │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  Q: 为什么主动干预用规则引擎而不是LLM？                                         │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: 4条硬编码规则 + 冷却时间控制                                     │    │
│  │  替代方案: LLM生成关怀消息                                              │    │
│  │  理由:                                                                  │    │
│  │  • 成本: 每4小时调LLM生成关怀，成本高                                  │    │
│  │  • 可预测性: 规则简单明确，"24h内负面>60% → 发关怀"                    │    │
│  │  • 冷却机制: 规则有冷却，LLM很难保证不重复打扰                         │    │
│  │  权衡: 规则不够灵活，但对于固定场景足够                                │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────────────────┘

│                              流式输出设计                                        │
│                                                                                 │
│  Q: 为什么流式输出用SSE而不是WebSocket？                                        │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: SSE (Server-Sent Events)                                         │    │
│  │  替代方案: WebSocket                                                    │    │
│  │  理由:                                                                  │    │
│  │  • 单向够用: 对话场景只需服务器→客户端                                 │    │
│  │  • 实现简单: fetch API + ReadableStream                                 │    │
│  │  • 自动重连: SSE内置，WebSocket需手动处理                               │    │
│  │  权衡: SSE不支持二进制，但对话只需文本                                  │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────────────────┘

│                              定时调度设计                                        │
│                                                                                 │
│  Q: 为什么定时调度器自己实现而不是用APScheduler？                                │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  决策: 60行自实现CronScheduler                                          │    │
│  │  替代方案: APScheduler                                                  │    │
│  │  理由:                                                                  │    │
│  │  • 功能够用: 只需要每日定时 + 间隔执行两种模式                          │    │
│  │  • 轻量: 60行代码，无额外依赖                                          │    │
│  │  • 跨天检测: 自实现更灵活                                               │    │
│  │  权衡: 不支持cron表达式和持久化，但项目够用                            │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │

│  ┌─────────────────────────────────────────────────────────────────────────┐    │

│  │  • 渐进式保证质量                                                       │    │
│  │  权衡: 需要更多时间，但保证每个阶段的质量                              │    │

💡 面试核心思路:
  • 每个设计决策都有"权衡"——不是说替代方案不好，而是在当前场景下这个更合适
  • 展示工程判断力: 知道什么时候该用复杂方案，什么时候简单方案够用
  • 诚实承认局限: "如果是大规模多用户场景，应该用xxx"
  • 用数据说话: 152条→30-40条，Recall@5=100%，0幻觉
